Paideia · local architecture proposal · 13 September 2026

The architecture, from YAML to a tested agent.

A native project and its environment, one YAML per dataset, and a bounded loop that evaluates and improves selected instructions.

Design stage. The example files, native declaration and real source hashes have been checked. Paideia’s runner, adapters, evaluators, DSPy bridge and viewer are proposed; no agent training has run.

01 / Components and ownership

Paideia surrounds the native agent.

The subject adapter runs the agent. The inference adapter supplies the optimizer and semantic judges. They are separate routes, even when they use the same subscription.

Paideia supplies a task, environment and limits. The agent chooses its own actions and tools.

Spawnfile prepares native workspaces. Daimon runs one agent. Moltnet transports messages. Mneme supplies memory. Paideia uses their public contracts.

Any native agent can be adapted. Missing observations or editable surfaces remain explicit; an adapter cannot invent evidence to make the same checks pass.

See the complete data flow and feedback path

The viewer reads persisted events, artifacts, scores and usage. Opening it does not run an agent, judge or optimizer. Production scheduling and deployment remain outside this loop.

02 / What the author writes

One native project. One YAML file per dataset.

The newsroom example has a Spawnfile, its Markdown environment, train.yaml, test.yaml and one README. Every record is inline. Other agents keep their own native project format.

YAML surfaceWhat it means
schema, id, subjectVersioned dataset identity and optional native agent identity.
setupA registered environment recipe: state, clock, delivery, source views and artifact collection. Newsroom behavior belongs in this integration.
records[].contextTyped setup/evaluator parameters such as edition and story ID; not automatically added to the prompt.
records[].inputThe actual task and exact selected source files. Each source has a resource, native-relative path and SHA-256.
records[].referenceEvaluator-only historical output. It is a comparison reference, not a gold answer or material for the agent.
stages, checks, gate, scoreA shared evaluation plan, applied to every record. Records can add criteria without weakening the shared gates.

The invocation selects project, subject, dataset roles, editable prompt sections, inference routes and budgets. Resolution creates a locked run manifest. There is no mandatory extra experiment YAML; invocation syntax is still to design.

How rules combine, from mechanical checks to prose quality
Rule familyConcrete meaning
MechanicalText contains/equals, schema validity, tool call existence/count and admitted artifact checks.
Ordered / correlatedSuccessful validation completes before the current accepted filing; the same article is filed under the actual active wake ID. Ordered matching permits repair attempts.
Logicalall, any, not, named rules, conditions and typed CEL predicates. CEL implementation remains to select.
SemanticA subscription judge evaluates fixed grounding and prose rubrics against declared evidence.
Embedding / customAn explicitly selected embedding provider, or a registered typed domain evaluator. Not exercised by these three records.
ProgressiveMechanics must pass before writing judges run. Writing score = 0.65 × grounding + 0.35 × prose; thresholds are proposed and need calibration.

Grounding must reach 0.90, prose 0.80 and the combined score 0.88. A good average cannot rescue a failed hard gate. Unknown, failed, errored and skipped results stay visible; missing evidence never counts as success.

Event order and evaluation order differ: a tool sequence checks what the agent did; a stage dependency decides when an evaluator runs. See the canonical YAML proposal.

03 / A single concrete execution

One Kestrel assignment, one isolated Scribe.

Subject: real Scribe prompts, Daimon with its Codex engine, real validator and filing tools, native source paths and memory interface.

Reconstruction: fresh assignment/state, empty memory and a clock starting on 12 September at 13:30 Berlin. This is not a historical replay.

Delivery: setup creates state without waking the agent. One authenticated Chief mention supplies the task and triggers the native wake. Message text is @scribe, one LF, then the YAML-parsed prompt.

Evidence: native calls and terminal outcome, accepted JSON, authentic filing/history receipts and the stored handoff to Reviewer.

SeamRequired behavior before this becomes a valid trial
Source selectionVerify revisions and file hashes. Preserve tools, schemas and catalogues; remove target/future output and all held-out content, including sibling reference outputs, every story derivative, aggregate byline rows, Git history, caches and memory paths.
IsolationFresh container, trial-owned volumes and native control credentials. Fixed native paths remain inside that container; they never mount production state.
Native preparationMatching attested runtime and original tool dependency closures. Candidate resource overlays must be supported through the native public contract.
Clock and wakeAgent, tools and runtime share the declared emulated wall clock. Capture the real active wake ID; do not substitute a record/message ID or submit a duplicate direct wake.
Accepted artifactA read-only collector joins current admitted filing, authentic receipt and committed bytes for this owner/edition/story. Validation JSON, admitted JSON, file hash and Git commit keep their separate identities.

A failed preflight prevents the paid run. A failed task is recorded; Paideia does not file an article on the agent’s behalf to repair its score.

Where sensors and multiple turns fit

These records use archived sensor packets; no live research is sent. A future research-loop record can use ordered turns: observe a real research request, then deliver a recorded or explicitly emulated response through Moltnet, and observe the resumed native agent. Paideia supplies external stimuli; the agent still decides whether to request research. No historical sensor-answer trace has been supplied for these records.

04 / How prompts change

Train on feedback; test after freezing.

Candidate sourceEditable areaHow the agent receives it
AGENTS.md“Prose and beat”Native instruction/config surface and workspace document, plus the mirrored public agent document.
RUNBOOK.md“Article craft”, “The article wake”, “Asking for research you do not have”The existing on-demand runbook path in the candidate’s isolated public source view.
SOUL.mdLockedPreserved in native and mirrored identity surfaces. Tools, policies, evidence and criteria also stay locked.

DSPy receives an explicit mapping of editable Markdown components. The native adapter prepares each candidate and verifies all effective destinations. Installing a file, observing it load and observing the agent follow it are separate claims. Changing a prompt requires a new native run; rescoring old traces is not a trial.

  • Inference: subscription routes for DSPy reflection and judging are selected independently of the subject. No silent paid-API fallback. Embeddings have a separate declared backend.
  • Selection: use training-only groups or an optional validation partition. Compare baseline and frozen candidate on the same test records, environment and evaluation plan.
  • Fair comparison: the normalized shared plan digest must match across train/test, including rubric/judge versions, thresholds and weights. Missing trials retain their denominator.
  • Local result: prompt diff, source/candidate identities, trace, quality, coverage, latency and separate subject/optimizer/judge usage. The viewer reads this ledger; deployment requires a separate decision.

The three retrospective newsroom records demonstrate authoring. They cannot establish statistical generalization or guarantee that a model has never encountered these public stories.
