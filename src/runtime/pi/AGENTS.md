# Pi Runtime Adapter

This folder lowers Spawnfile agents into a generated Pi SDK application.

- `adapter.ts` validates model support and emits per-agent workspace files.
- `containerTargets.ts` merges Pi agents into one container target and emits the generated runtime artifacts.
- `appTemplate.ts` is the stable entry point for generated Pi package/config artifacts; `appTemplateTypes.ts` owns the generated-agent contract and shared option constants, while `appAgentConfig.ts` resolves agent, model, memory, and schedule configuration.
- `appScriptedEngine.ts` resolves the `scripted` engine's `engine_command` manifest option and the in-workspace staged path it is copied to (`SCRIPTED_ENGINE_STAGED_DIRECTORY`), shared by `appTemplate.ts` (records `engine_command` in the generated `pi-app.json`) and `adapter.ts` (stages the actual script file). Split out of `appTemplate.ts` to stay under the 400-line limit and to avoid a circular import (it deliberately checks `node.runtime.options.engine === "scripted"` directly rather than calling `appTemplate.ts`'s `resolvePiEngine`).
- `appCliEnginesSource.ts` renders each generated CLI-backed engine (`codex`/`claude`/`grok`/`agy`/`scripted`) and the shared `runCliEngine` dispatcher. The `scripted` branch (`runScriptedEngine`) execs the staged script (`path.join(paths.workspacePath, config.engine_command)`) under plain `node` with the PINNED argv contract `--prompt-file <path> --cwd <workspacePath>` — the same contract `src/e2e/officeSimEngines.ts`'s fake `grok` binary already speaks, preserved byte-for-byte so a canned screenplay can move into a `scripted`-engine fixture unchanged. Script stdout (trimmed) is the reply text; no ANSI/progress-line cleanup is applied (unlike the other CLI engines) since a scripted script's output is exact by construction. Each call appends one JSON line to `<runtimeHomePath>/scripted-engine-calls.jsonl` — next to (a sibling of) the agent's `telemetry/` directory, never a host bind-mount or the old `SPAWNFILE_FAKE_ENGINE_LOG_DIR` env var.
- `appSource.ts` composes the generated runtime application source.
- `appPreludeSource.ts` renders generated imports and shared helper functions.
- `appScheduleSource.ts` renders the importable timer installer shared by the generated app and artifact-level schedule tests.
- `appActivitySource.ts` renders the bounded activity broker and activity HTTP/SSE endpoints.
- `appControlSource.ts` renders generated control endpoints for wake, activity, and dev-time agent reloads; `appControlWakeIdentitySource.ts` isolates the generated wake identity/token constants and causal-id helper. Wake is split into two endpoints by authenticating authority (B62 Option B): `POST /agents/:slug/wake` is the Moltnet->Pi loopback delivery endpoint (never gated by `SPAWNFILE_PI_CONTROL_TOKEN`, stamps `control.wake.accepted` with principal `system:moltnet` via daimon's `emitDeliveryWakeAccepted`), and `POST /spawnfile/agents/:slug/wake` is the operator-only endpoint (fail-closed on `SPAWNFILE_PI_CONTROL_TOKEN`, stamps `operator:control` via `emitControlWakeAccepted`/`emitControlWakeDenied`). Both share one `executeAgentWake` wake-execution helper; only auth and attribution differ.
- `appWakeContextSource.ts` renders generated Moltnet/team-context wake resolution helpers.
- `appCoreSource.ts` renders the generated runtime application that starts Pi sessions, exposes the Moltnet wake control endpoint, and runs scheduled wakes.
- `runAuth.ts` adapts imported Codex auth into the Pi auth-store shape at run time.

`PI_ENGINE_KINDS` (`appTemplate.ts`) includes `scripted` (Piece 5, Slice B): a Spawnfile agent declares `runtime: pi` with `options: { engine: scripted, engine_command: <fixture-relative script path> }` to get a deterministic canned-reply engine with no real model auth and no host-side fakes, replacing the `injectFakeEngines` (bind-mount-a-fake-`grok`-over-`/usr/local/bin/grok`) test-only hack. `adapter.ts`'s `validateRuntimeOptions` requires `engine_command` whenever `engine: scripted`; `compileAgent` then stages that script (read once via `resolveProjectPath(node.source, ...)` + `readUtf8File`, the same manifest-relative-path convention `surfaces.ts`'s `loadResolvedDocuments`/`loadResolvedSkills` use for docs/skills) as a `workspace/engine/<basename>` `EmittedFile` with `mode: 0o755`, which `createContainerTargets`'s existing `moveWorkspaceFileToAgentWorkspace` relocates to `workspace/agents/<slug>/engine/<basename>` exactly like every other per-agent workspace file — no new staging mechanism. `createContainerTargets` also computes an `engineByNodeId` map (node id -> resolved engine kind) and attaches it to the returned `ContainerTarget`; `src/compiler/containerArtifactsPlans.ts`/`containerArtifacts.ts` thread it through unchanged into `ContainerRuntimeInstanceReport.engine_by_node_id` (`src/report/types.ts`) for every pi/daimon runtime instance (not just `scripted` — any resolved engine kind is disclosed), and `src/compiler/upReceipt.ts`'s `buildUpReceipt` flattens that same map into the up-receipt's optional `engines: [{agent, engine}]` disclosure field. There is no test-only branch anywhere in this path: `scripted` is a normal, first-class engine declaration.

Keep Pi-specific generation here. Generic container rendering belongs in `src/compiler/`.
